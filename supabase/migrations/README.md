# Database migrations

`supabase-schema.sql` (repo root) is the original baseline — a single
idempotent file safe to paste into the Supabase SQL Editor for a fresh
project. It's kept as-is for that purpose.

Everything from here on is a **tracked, ordered migration** in this folder.
Run them in filename order (they're timestamp-prefixed) in the Supabase
SQL Editor. Each file is idempotent where practical (`IF NOT EXISTS`,
`CREATE OR REPLACE`, `DROP ... IF EXISTS` before `CREATE`), so re-running
one that already applied is safe.

If you later install the Supabase CLI, this folder already matches its
`supabase/migrations/` convention — `supabase db push` will pick these up
directly.

| File | What it does |
|---|---|
| `20260709000001_trip_members.sql` | Adds real multi-user trip support (`trip_members` table + RLS rework + join-by-code RPCs). Backfills existing trips so current owners don't lose access. |
| `20260709000002_drop_redundant_trip_columns.sql` | Drops the `trips` columns that duplicated the `data` JSONB blob and were never queried directly. |
| `20260709000003_validation_constraints.sql` | Adds size/shape CHECK constraints as a backstop, since clients write to Supabase directly (no API layer validates first). |
| `20260709000004_packing_state_membership_and_index.sql` | Requires actual trip membership (not just row ownership) to read/write `packing_state`; adds a missing index on `trip_members.user_id`. |
| `20260709000005_fix_trip_members_rls_recursion.sql` | Fixes an infinite-recursion bug in trip_members' own SELECT policy, found via live testing after 0001. Not currently hit by the app (nothing does a direct client SELECT on trip_members yet) but was broken SQL. |
| `20260709000006_fix_packing_state_policy_not_applying.sql` | Live re-test after running 0004 showed non-members could still write `packing_state`. Root cause: an older-named policy (`"Users can manage own packing state"`) was never dropped, and Postgres combines multiple permissive policies with OR — the old unrestricted one alone let writes through. Drops all known legacy policy names on `packing_state` and `trips`, then lists the actual resulting policies so the fix is visible immediately. |
| `20260709000007_temp_policy_audit_function.sql` | Temporary — adds `_diag_list_policies()` so every table's RLS policies can be listed via one RPC call, catching the same "orphaned legacy policy" class of bug as 0006 anywhere else it might exist. |
| `20260709000009_drop_undocumented_legacy_policies.sql` | The audit (0007) found the *real* root cause 0006 missed: a third, completely undocumented policy (`"own packing"`) predating even supabase-schema.sql's own comments, with no membership check — Postgres OR-combines permissive policies, so it alone let non-members write `packing_state` regardless of 0006's fix sitting right next to it. Also drops the same undocumented pattern on `trips`/`profiles` (not currently causing a bug there, but same leftover). **Run this before 0008** — it uses `_diag_list_policies()` to show the result inline. |
| `20260709000008_drop_policy_audit_function.sql` | Cleanup for 0007 — drops `_diag_list_policies()`. Run this *last*, after 0009. |
| `20260709000010_social_features.sql` | Adds `get_trip_member_profiles()` (real trip-mate avatars/names), `get_my_packmates()` (real contacts, derived from shared trip history instead of the old localStorage mock list), and `get_discoverable_travelers()` + a new opt-in `profiles.discoverable` column (default OFF) for real users in Community Travelers — no one is shown to others without explicitly turning this on. |
| `20260709000011_member_management.sql` | Adds `remove_trip_member()` (owner-only) and `add_packmate_to_trip()` (owner-only, and only for someone already a real packmate of the caller — a stranger can still only join via invite code). |
| `20260709000012_notification_context.sql` | Adds `trip_members.added_by` (who performed the insert — self for a voluntary join, the owner for a direct add) so the client can tell the two apart and notify the added/removed person themselves, not just the trip owner. Also enriches `get_my_packmates()` with `first_shared_trip_id`/`first_shared_destination` so the client can show "packmates since &lt;trip&gt;". |
| `20260709000013_real_profile_richness.sql` | Adds `profiles.bio`/`profiles.location` — the profile.html inputs for these already existed but were never actually persisted to Supabase, only localStorage. Enriches `get_discoverable_travelers()` with real `bio`, `location`, `member_since`, and an aggregate-only `trip_count` (never destinations) so a real user's Community Travelers card shows genuine data instead of blank fallbacks. |
| `20260709000014_fix_trip_creation_upsert_rls.sql` | **Critical fix** — every new trip creation was silently failing. `trips` had separate `FOR INSERT`/`FOR UPDATE` policies (identical conditions, but split), and Postgres's RLS handling of `INSERT ... ON CONFLICT DO UPDATE` (what Supabase JS's `.upsert()` sends) doesn't work reliably with split per-command policies — confirmed via live A/B test against `packing_state`, which uses one unified `FOR ALL` policy and works fine with the identical upsert pattern. Replaces the split policies with one `FOR ALL` policy. |
| `20260709000015_add_packing_finished.sql` | Adds `packing_state.finished` — backs the packing-list "Finish Packing" toggle so it syncs across devices instead of only living in localStorage. **Run this before deploying any client code that upserts a `finished` field to `packing_state`** — until it's applied, that upsert would fail (unknown column) and take the whole row (item_state/dismissed/custom_items too) down with it. |
| `20260729000001_add_welcome_email_sent.sql` | Adds `profiles.welcome_email_sent`, gating `api/send-welcome-email.js`'s one-time welcome email so a retry or multi-tab race can't double-send it. **Run this before deploying `api/send-welcome-email.js`** — until it's applied, the endpoint's claim-the-send `PATCH` will fail (unknown column) and every request will 500. |
| `20260729000002_weekly_newsletter.sql` | Adds the `newsletters` table (self-service content queue — edit rows directly in Supabase Studio's Table Editor, no deploy needed), `profiles.newsletter_unsub_token`, and the `unsubscribe_newsletter()` RPC backing the one-click unsubscribe link. **Run this before deploying `api/send-newsletter.js` / `api/unsubscribe-newsletter.js`** — until it's applied, both 500 (unknown table/column/function). |
| `20260729000003_newsletter_header_image.sql` | Adds `newsletters.header_image_url` — optional per-week hero image (a real public https URL) that replaces the default gradient+logo+headline header when set. Purely additive; a blank value keeps the default header. |
| `20260729000004_newsletter_send_window.sql` | Adds `newsletters.send_after` / `send_before` (both optional dates) — a row outside its window is skipped by `api/send-newsletter.js` in favor of the next eligible queued row, staying `queued` rather than firing late (e.g. a summer-themed send that never went out won't fire once it's out of season). |
| `20260729000005_default_newsletter_optin.sql` | Updates `handle_new_user()` so every **new** signup's profile row starts with `notif.updates = true` (Settings' "Weekly Newsletter" toggle) instead of unset/off. Existing users are untouched — this only changes what a brand-new profile gets. |
| `20260729000006_newsletter_layout.sql` | Adds `newsletters.layout` — optional per-week alternate body design (`checklist` / `icon-grid` / `badges`, or legacy `city-checklist` / `cold-checklist`) with themed icons instead of the default icon-showcase-then-paragraphs layout. Left blank, a row renders exactly as before. |
| `20260730000001_newsletter_stat_columns.sql` | Adds `newsletters.stat_caption` / `stat_left` / `stat_right` / `stat_footer` — generalizes the stat callout box (originally hardcoded 40°F/20°F for the cold-weather send only) so any `checklist`-layout row can opt into one. Left blank, no stat box shows (except the already-queued cold-weather row, which falls back to its original hardcoded copy). |
